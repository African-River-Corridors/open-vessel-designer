- Tank top above the deck (issue #992, phase 1): a new gas input `tank_top_above_deck_m`, the height of the top of the tank shell above the main deck at the side. 0 is tanks in hold. Left out (the default, and what a file saved before holds), nothing changes: the depth is the one typed, or the depth-to-beam ratio default, and every result is unchanged. Set, the depth of each arrangement the search tries follows its tank: the double bottom, the support and the tank outer diameter, less this height, to the millimetre (at 0 the deck stands 0.3 m above the tank top, an estimate). The depth is settled by repeating the build, because the bow rake, and so the tank, depends a little on it. A height above the tank diameter is turned down with the reason in the arrangements tried. A typed `moulded_depth_m` wins over the input, with a warning. Results carry `arrangement.tank_top_above_deck_m`, `tank_top_above_keel_m` and `depth_follows_tank` only when the input is set. The Defaults Profile holds the later default by Service Area as the rule `tank_top_above_deck_default_rule` (coastal 2.0 m, river only half the tank outer diameter); it is read and checked, and not applied yet.
- Hydrostatic table (issue #992): its last row is at the exact depth, not at `depth * 10 / 10`, which can be one floating-point step above the depth (14.684 m is one) and has no waterplane, so a hull of that depth failed. No fixture, website example or worked example hash moves (`tools/check_fixture_hashes.py` matches every one).
- Files (issue #992): the current fixtures, the website gas example and the sensitivities example store the new input as none (default); a file saved before still gets it as a fixed value with a note.
